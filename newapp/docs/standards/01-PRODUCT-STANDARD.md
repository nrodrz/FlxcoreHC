# 01 · Product Standard — ownership, white label, licensing, updates, data

Standards 1.1 · 10/27/2026

What every app of the owner does and shows, the same way, whatever its subject. `<Product>` is the app's name and
`<prefix>` its prefix (see README).

## 1. Purpose

1. **Ownership is visible and fixed.** The owner, the copyright and the license terms are in the code and shown in the
   same places in every app. Nothing in the app can change them.
2. **The product is neutral.** Screens, messages, documents, examples, seed data and tests name no customer
   organization, none of its people, domains or hosting provider.
3. **Each installation is its own.** The organization's name, domains, scheduled-job lines, time zone and data come from
   that installation's settings or files, never from the code.
4. **Each app is its own ecosystem.** Its own License Hub, keys, clients and installations; no hub licenses another app.

Scope: program files, built assets, documents shipped with the app, help content, generated guides, seed and update
data, test fixtures and the install package. The organization's own data stays as it is.

## 2. Owner facts and exact wording

Kept as constants in one ownership file per app. Only the product name and product line change from app to app.

| Item | Value |
| --- | --- |
| Owner | Indisse-BTS (no person is named as owner in any app) |
| Copyright years | 2026 (later years extend it, e.g. 2026–2027) |
| Copyright line | © 2026 Indisse-BTS. All rights reserved. |
| Source-file header | © 2026 Indisse-BTS. All rights reserved. Proprietary — licensed, not sold. See LICENSE.txt. |
| Product line | One short line per app, set in its ownership file |

Developed-by sentence: `<Product>` is designed, developed and owned by Indisse-BTS, drawing on 30 years managing IT
operations for multiple companies in Puerto Rico and Florida.

Independent-developer statement: `<Product>` is an independent product. It was conceived, designed and developed by
Indisse-BTS as an independent software developer, and not as an employee, contractor or consultant of any company or
organization. It was not commissioned by, and is not a work made for hire for, any organization that uses it.
Licensing, using, testing or requesting features of `<Product>` gives no organization any ownership interest in it, in
its updates, or in improvements made at its request.

License terms in short (eight lines, in this order):

1. `<Product>` is proprietary software. It is licensed, not sold.
2. Each organization uses `<Product>` under its own written license agreement with the owner. That agreement sets the
   term, the installation, the number of users and the modules.
3. A license does not transfer ownership of the software, its source code, design, database structure, documentation,
   or any change or improvement made to it.
4. Unless the license agreement allows it in writing: no copying beyond the licensed installation and its backups, no
   redistribution, sublicensing, resale or hosting for others, no reverse engineering, and no removal of these notices.
5. The licensed organization owns its own data. The owner of `<Product>` claims no right to it.
6. Names of other products, services and agencies only identify what `<Product>` connects to or works with. They belong
   to their owners and imply no affiliation or endorsement.
7. Ideas, requests, feedback or testing by an organization do not make it an owner or co-author of `<Product>` or of any
   feature made from them. Every update, module and customization belongs to the owner and is licensed under the
   organization's agreement.
8. The owner is an independent software vendor, not an employee or agent of any licensed organization. Any other work
   the owner does for an organization is separate from the license and transfers no right in `<Product>`.

Only the examples an app adds to line 6 may differ. All texts are drafts for attorney review and must match the
Software License Agreement and Terms of Use in force.

| 8 | Installation ID | About & ownership | `XXXX-XXXX-XXXX-XXXX` uppercase hex, random, made once, never editable; sent only to the app's own License Hub |

| View | Who | Fields, in order |
| --- | --- | --- |
| Sign-in page | Everyone | Product · copyright line · "Proprietary software, licensed, not sold." |
| Short view | Everyone signed in | Product and line · developed-by sentence · independent-developer statement · copyright · version · licensed to · open-source note |

## 4. Naming rules

| Kind | Rule | Instead |
| --- | --- | --- |
| Customer organization | Banned everywhere | "the organization", or the name from settings |
| Its people | Banned | Roles or made-up names |
| Its domains, sites, cities | Banned | example.com, example.org, example.onmicrosoft.com; made-up places |
| Hosting provider | Banned in code and data | Neutral keys ("hosting") |
| Standards bodies, regulators, frameworks | Banned | Neutral control areas ("Patch management") |
| Other products the app connects to | Allowed, only to say what it connects to | — |
| The owner's other apps | Never named in each other's text | "a companion app" |
| Code identifiers already in use | Kept when renaming would break installations | — |

Made-up data: invented names, "Client AA", test numbers in a reserved range; one real name always maps to the same
made-up name. Sweep tests build their patterns from pieces; real names live only in an outside list, never in the repo.

## 5. Per-installation values

| Value | Comes from | Rule |
| --- | --- | --- |
| Organization name ("Licensed to") | Settings | ≤ 120 characters, audited old → new |
| Name shown to people | Branding, else the product name | Never the owner's |
| Scheduled-job lines | Built at run time from the PHP binary and install path | No domain or account path in code |
| Domains and addresses | The installation's address and its own settings | Defaults empty |
| Integrations | Set up only when configured | — |
| Installation data files | A private folder next to the configuration | Shipped separately; the feature says what is missing without them |
| Secrets and keys | Typed by an administrator in the app | Wrapped; never returned, logged or packaged; never sent in chat |
| Time zone | Per-installation setting (installer and settings) | Every screen and entry point; 12-hour times, MM/DD/YYYY dates; a later change asks for confirmation |

## 6. Data rules

- An installation's records, settings, audit rows and files are never changed by white-label work; moved settings go
  through a database update that keeps the value.
- No real people, clients, notes, numbers, emails, phones or addresses in fixtures or tests.
- A fixture that held real data travels as a whole replacement file, never as a change block.
- Seeds use generic names that point to no real organization or place.
- Installation data files travel separately from the product package.
- Screenshots and guide figures use demo data only.

## 7. Licensing: each app's own License Hub

Every app is licensed the same way: a signed license file per installation, issued from that app's own main
installation (its License Hub), run by the owner.

**The license file.** A PHP file next to the configuration (`<prefix>-license.php`) that only returns an array. Signed
fields, in this order: serial, agreement, licensee, install_id, kind, plan, modules, users, term_start, term_end, notes,
issued_at. Signature: Ed25519 over those fields as JSON, with `key_id` and `signature` beside them.

- Builds carry only the public half of the license key; the private half lives on the hub (wrapped with its vault key)
  and in a passphrase-protected backup (Argon2id + secretbox), kept in two safe places.
- Genuine file for this installation within its term → its plan and modules. Term ended → 14 days of grace. No file,
  changed, unsigned or another installation's → a 30-day trial with everything, then only the core. Nothing is deleted.
- Apps sell plans (sets of modules) plus extra modules; the license decides what is on; a Super Admin can only switch
  modules off.
- A file written from a hub answer is written by the installation from the checked fields, never from bytes received.

**Two installers in every package.**

| Installer | For | Adds |
| --- | --- | --- |
| `install/` | Every organization | Optional step "License Hub": paste a link code. Afterwards it deletes the hub installer; updates never bring it back on a licensed installation |
| `install/hub.php` | The app's one main installation | The hub's HTTPS address, organization, backup passphrase. Turns the License Manager on, creates the license key and the release key, issues its own license, offers both key backups once and shows both public key lines for the builds |

Both installers lock once the app is installed. The installer's last page uses no inline script (security policy).

**Link codes and the daily check-in.**

- A link code carries the hub's address and a token, made on the hub for an installation ID or for the next
  installation that uses it within 30 days. Shown once; the hub keeps only its hash; the installation keeps it wrapped.
- Once a day the installation checks in over HTTPS and sends only: installation ID, build, PHP and database versions,
  active users, last update result, license number in use, license state, last problem. Nothing about people, records
  or settings.
- The hub answers with the newest license, signed revocation notices, and the build offered. A license counts only with
  a valid signature for this installation; a revocation only when signed and naming this installation and its license.
- The installation can switch check-in off or unlink and keep receiving files by hand. The hub never logs in to a
  client's server.
- The License Manager has five tabs: Licenses, Clients, Billing, Installations, Releases.
- Every call an installation makes to its hub (check-in, update download) sends a User-Agent naming the product, "License
  Hub" and the build (`<Product>-LicenseHub/<build>`). Shared hosting filters refuse requests without one.
- The installation's message says who refused and why: the hub's own reason when the hub answered; "blocked before it
  reached the License Hub", with the answering server's name and the start of its text, when something in front of the
  hub answered. A check-in with no license issued says exactly that (and the trial date), never "the license is
  current"; with a license it names the license number.
- Changing what a client may use is done by "Renew / change" on its license: the new license reaches the installation at
  its next check-in; the modules it no longer names leave the menu and are refused for everyone, their data kept.
  Revoking is different: a revoked installation has no license and runs on the trial until its date, then only the core.
- A free client gets a license like any other (kind Free, plan and modules as agreed, billing none).

## 8. Terms of Use

- The same Terms in every app, with its own product name; they bind organizations and users without a signed contract,
  free installations included. A signed license agreement, where one exists, prevails.
- The Terms name the organization and the product; the owner only in the independent-developer term. The effective date
  is the installation's start.
- Accepting for the organization is its own permission (Super Admin by default): a person ticks "I have authority to
  accept these Terms for [organization]" and agrees.
- Each user's first sign-in shows the full Terms with I agree / Sign out; nothing opens until accepted. Every acceptance
  is an audit row (user, organization, version, date and time).
- Material change → new version, everyone accepts again. Minor change → notice; continued use after 30 days is
  acceptance. The text ships with the app and cannot be edited from a screen.

## 9. Updates and releases

- A signed bundle: `manifest.json` (build, notes, package size and BLAKE2b-256 hash, database update yes/no, optional
  installation ID) signed with the release key, plus `package.zip` (the full install package). The release key is
  separate from the license key, with its own backup.
- Check before any change: signature, package hash, build newer than installed, free space, write access, every PHP
  file parses.
- Install in two steps with a backup: (1) old code: database backup, copy of the files it replaces, maintenance mode
  (ends by itself after 15 minutes), new files; any failure puts the old files back. (2) new code: database update,
  maintenance off. The previous build can be put back from any of the three newest backups.
- Never touched: configuration, license file, private data folder, uploads, `.user.ini`, `php.ini`, the hub installer
  on a licensed installation.
- Channels on the hub: Pilot first, Stable after a waiting period (7 days by default) or when promoted; pause, resume,
  withdraw. A Super Admin approves each update unless a maintenance window is on. Everything is audited on both sides.

## 10. Clients and billing (on the hub only)

- No money moves through any app; nothing about prices reaches a client.
- Clients: organization (unique), contact, email, phone, address, notes. A license is issued to a client.
- Price list per plan and module, monthly and annual: a base price including some users, plus a price per extra user.
  A new price starts on its date; an issued license keeps its price.
- Charges (one per period, numbered), payments by hand (partial allowed), void with a reason, never delete. Status,
  aging, balance per client, CSV export with spreadsheet formulas made harmless.
- Overdue is a warning only; nothing is held or revoked automatically. US dollars; no tax line.

## 11. Data dictionary

Every app shows its own data the same way: Administration → Data, Super Admin only.

- Overview and report: every table with what it is for, rows and size; empty tables; tables no code uses; families of
  similar tables with advice on merging.
- Grid: filter under every column (contains, `=` exact, `!` not, `>` `<`, `^` starts, `empty`, `!empty`), sort, group
  with counts, export to Excel or CSV (up to 50,000 rows, formulas made harmless).
- Dictionary per table: column, type, empty allowed, default, keys, the table it points to, what it holds.
- "Download the dictionary": the whole dictionary as one document, written from the live database.
- Changes: only chosen columns of reference lists, checked against the column; a value changed meanwhile is refused.
- Secrets are never shown, filtered, sorted, grouped or exported.
- Audit: viewing rows (once an hour per person and table), every export, every change, every refusal.
- Changing the database structure (merge, split, remove): the report first, the owner decides, then one database update
  as in `03-DEVELOPMENT-PROCESS.md`.

## 12. Transfer of ownership or renaming

Owner and product facts cannot be changed from the app; they live in a few known places, so a sale or rename is a short,
scripted change: sign the transfer first; run the app's rebrand script (constants, headers, banner, LICENSE.txt, About
texts); keep third-party notices and internal code names; run the ownership test (the old owner must be found nowhere);
ship as an ordinary update; issue new license files as agreements are reassigned.

## 13. Verification (every app)

- [ ] About & ownership returns every field as written here; the short view carries no full-view field.
- [ ] Sign-in shows the Powered-by line and the Terms link.
- [ ] Organization name saves and is audited old → new; installation ID made once and stable.
- [ ] Every program file has the header; LICENSE.txt and THIRD-PARTY-NOTICES.txt in the package.
- [ ] The names sweep finds nothing; no domain, account path or name in code.
- [ ] A genuine license file turns on its plan and modules; a changed one, another installation's or one without the
      right key is refused and changes nothing.
- [ ] A signed bundle installs in two steps and can be put back; a changed bundle is refused before anything changes.
- [ ] The data dictionary describes every table of a fresh installation; no secret in any answer or export.
- [ ] Deleting a record of every kind moves it to Deleted items with its children; put back restores it with the same
      number and links; delete for good removes it and its files; a record still used by others is refused (14).
- [ ] The permission validator and the role matrix pass (15).
- [ ] A check-in through a host filter that refuses requests without a User-Agent succeeds; a blocked one names the
      blocker (7).
- [ ] Negative control: the same tests fail on the build before adoption.

## 14. Deleted items (recycle bin)

Every app deletes the same way: nothing a person deletes is erased at once. It goes to **Administration → Deleted items**
and can be put back exactly as it was, or deleted for good.

- The record and the rows that belong to it (its children) are kept together as one entry, then removed from their
  tables, so every list, search, report and export behaves as if they were gone. Files stay on disk until the entry is
  deleted for good.
- Links that a delete clears on other records are written down with the entry and set again on put back where they are
  still empty.
- A record that other records still depend on is not deleted at all: the answer names what uses it and suggests setting
  it inactive.
- Side effects already done (a notification sent) are not undone by putting back.
- The page: one list of entries, newest first: kind, name, related rows and files, who deleted it, when, and the date it
  will be deleted for good. **Put back** (same numbers), **Delete for good** (typed `DELETE`), **Empty** (typed
  `EMPTY`, Super Admin only), **Kept days** (30 by default; the scheduled job deletes older entries daily).
- A permission `Deleted items` with View, Edit (put back), Delete (delete for good); a person sees only the entries of the
  parts of the app their role can see, and each action also needs the same action there.
- Every delete, refusal, put back, delete for good, empty, change of kept days and automatic deletion is an Audit Log entry.

## 15. Roles and permissions

- Every permission a server check uses has a row in the Roles editor, and every row is checked somewhere. Each row lists
  exactly the actions the server checks for it (View, Create, Edit, Delete, All, Admin). A permission no role can be
  given is a defect.
- A permission of a sold module belongs to that module in the manifest: when the license does not name the module, the
  permission is refused for everyone, Super Admin included, and the module's pages leave the menu; data is kept.
- A sub-permission that only works with a base permission declares its base. The Roles editor ticks the base when the
  sub-permission is ticked and clears the sub-permission when the base is cleared; a role saved through the API gets the
  base added.
- Lists that reveal who receives work, counts or settings are for the permission that manages them; people who only use
  them get the short form.
- Every build that touches permissions runs two checks: the **permission validator** and the **role matrix** (one role
  per permission: a role with nothing gets no data; a role sees no data of another module; each permission opens its own
  module; a view-only role writes nothing).
